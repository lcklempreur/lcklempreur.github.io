Centralisation et analyse des journaux système

rsyslog + Filebeat + Elasticsearch + Kibana

Contexte et objectifs

La centralisation des journaux système est une pratique fondamentale en infrastructure IT. Elle permet de superviser efficacement les systèmes, diagnostiquer rapidement les incidents, renforcer la sécurité par la détection d'anomalies et garantir la traçabilité des actions.

Ce projet met en place une solution ELK (Elasticsearch, Filebeat, Kibana) complète intégrée dans un environnement Active Directory existant avec Ubuntu Server 24.04 LTS comme serveur central de logs.

Infrastructure déployée

Machine Adresse IP Rôle
ubulog (SRV-RSYSLOG) 192.168.10.1 Ubuntu Server 24.04 LTS – rsyslog (collecte) + Filebeat (transfert) + Elasticsearch 8.x (indexation) + Kibana (visualisation)

SRV-AD 192.168.10.10 Windows Server – Contrôleur de Domaine (srvlog.lan) + DNS. Authentification des utilisateurs Linux via Kerberos/SSSD

Flux de centralisation des logs

Clients (syslog) → rsyslog:514/TCP
↓
Templates JSON → /var/log/central/**/all-json/*.json
↓
Filebeat → Elasticsearch (index rsyslog-logs)
↓
Kibana (dashboards + alertes)

Travaux réalisés

1. Configuration du serveur rsyslog (collecte et structuration)
  • Activation réception TCP port 514 (module imtcp)
  • Template JSON RFC3339 : @timestamp, hostname, programme, sévérité, message
  • Arborescence : /var/log/central/hostname/categorie/YYYY-MM-DD.json
  • Règles de tri par programme : sshd, sudo, systemd, kernel, apache2, nginx, NXLog Windows
  • Configuration clients Linux : *.* @@192.168.10.1:514 (relais TCP fiable)
2. Déploiement Elasticsearch 8.x (stockage et indexation)
  • Ajout dépôt Elastic official (GPG key + signed-by)
  • Installation avec génération automatique mot de passe elastic
  • Certificats SSL auto-générés et configuration HTTPS
  • Configuration snapshots : path.repo: ["/var/backups/elasticsearch"]
  • Vérification santé cluster : curl -k -u elastic:password https://localhost:9200
3. Déploiement Kibana (interface de visualisation)
  • Installation kibana + génération token d'enrôlement pour Elasticsearch
  • Configuration 3 clés xpack obligatoires : encryptedSavedObjects, reporting, security (32 chars min chacune)
  • Permissions certificats SSL : chmod 755 /etc/elasticsearch/certs/ && chmod 644 http_ca.crt
  • Kibana groupe elasticsearch pour accès certificats
  • Accès sécurisé : http://192.168.10.1:5601 (réseau interne uniquement)
4. Installation Filebeat (transfert JSON vers Elasticsearch)
  • Collecte fichiers JSON : /var/log/central/**/all-json/*.json
  • Configuration multiline : json.keys_under_root + json.add_error_key + json.message_key
  • Output Elasticsearch : hosts https://localhost:9200 avec username/password (elastic)
  • Index destination : rsyslog-logs (sans ILM pour contrôle manuel)
  • Vérification : curl -k -u elastic:pass https://localhost:9200/rsyslog-logs/_count
5. Création Data View et dashboards Kibana
  • Data View : pattern rsyslog-logs* avec timestamp field @timestamp
  • Dashboard Centralisation Logs : tableau des machines actives, camembert par programme, bar chart temporel par hostname
  • Dashboard Authentification SSH : compteur total SSH, tableau sévérité, bar chart temporel, compteur Failed password
  • Vue Discover : logs SSH en temps réel avec KQL filter program : "sshd"
6. Système d'alertes Kibana (détection brute force)
  • Rule type : Elasticsearch query
  • KQL : program : "sshd" and message : "Failed password"
  • Condition : WHEN count() IS ABOVE 5 FOR THE LAST 1 minute
  • Fréquence : Every 1 second
  • Status Active (rouge) quand alerte déclenchée
  • Accès : Stack Management > Rules > Alerte Brute Force SSH > onglet Alerts
7. Sécurité réseau et pare-feu UFW
  • SSH : port 22/TCP (accès illimité)
  • rsyslog : port 514/TCP et 514/UDP (collecte logs)
  • Elasticsearch : port 9200/TCP (accès interne uniquement)
  • Kibana : port 5601/TCP → seulement depuis 192.168.10.0/24 et 192.168.209.0/24 (NAT)
  • sudo ufw enable && sudo ufw status verbose
8. Archivage et maintenance (rotation + backups)
  • Logrotate : /etc/logrotate.d/central-logs → rotation quotidienne, 180 jours rétention, compression .gz
  • Archive directory : /var/log/archives/ (chown syslog:adm)
  • Snapshots Elasticsearch : script /etc/cron.daily/elasticsearch-snapshot (sauvegarde quotidienne dans /var/backups/elasticsearch/)
  • Repository backup_logs configuré via API curl -X PUT _snapshot/backup_logs

Incidents rencontrés et solutions

① omelasticsearch incompatible Elasticsearch 8.x (HTTPS)

Module rsyslog omelasticsearch v8.2112 ne supportait pas HTTPS → logs jamais envoyés, aucune erreur visible, index rsyslog absent.

✅ Solution : remplacement par Filebeat (outil officiel Elastic supportant nativement ES 8.x + HTTPS)
② Guillemets typographiques corrompant config rsyslog

nano remplaçait guillemets droits par guillemets typographiques. rsyslog affichait : "invalid character - is there an invalid escape sequence?"

✅ Solution : utilisation sudo tee avec heredoc (tee << 'EOF') pour écrire fichiers config (ASCII pur)
③ JSON multiline – plusieurs objets par ligne

Template rsyslog générait plusieurs objets JSON collés. Filebeat attendait 1 objet/ligne → affichait "events filtered" au lieu de "events acked".

✅ Solution : ajout \n en fin template JsonFormat : constant(value="\"}\n")
④ Kibana crash – permissions certificats SSL Elasticsearch

Après réinstall Elasticsearch : FATAL Error: EACCES permission denied /etc/elasticsearch/certs/http_ca.crt

✅ Solution : chmod 755 /etc/elasticsearch/certs/ && chmod 644 http_ca.crt && usermod -aG elasticsearch kibana
⑤ Cluster Elasticsearch état RED (snapshot restore)

Après test restauration snapshot, index resté RED → unassigned_shards bloquait cluster entier sur 1 nœud.

✅ Solution : DELETE _data_stream/restored_rsyslog-logs via API curl
⑥ Kibana alertes – clé chiffrement xpack manquante

Impossible créer règles d'alerte : "You must configure an encryption key to use Alerting"

✅ Solution : 3 clés xpack 32chars dans kibana.yml (encryptedSavedObjects, reporting, security) + systemctl restart kibana
⑦ Alerte Brute Force SSH – KQL + fenêtre temporelle

Alerte exécutée (Succeeded) mais sans déclencher Active alerts. Erreurs : (1) KQL ciblait program au lieu de message ; (2) fenêtre 1 seconde trop courte.

✅ Solution : KQL correcte program:"sshd" AND message:"Failed password" + fenêtre "FOR THE LAST 5 minutes"

  • ✅ Logs Linux centralisés en JSON, indexés temps réel, consultables 24/7
  • ✅ 2 dashboards Kibana fonctionnels : Centralisation Logs + Authentification SSH
  • ✅ Système d'alertes brute force SSH actif (détection < 1 minute)
  • ✅ Archivage 180 jours + compression .gz dans /var/log/archives/
  • ✅ Snapshots Elasticsearch automatisés quotidiennement (cron)
