Centralisation des logs – rsyslog + ELK Stack

Projet
BTS SIO SISR – E6
Période
Décembre 2025 – Mars 2026
Serveur
ubulog – Ubuntu Server 24.04 LTS
Domaine
srvlog.lan

Stack technique

rsyslog Filebeat Elasticsearch 8.x Kibana NXLog Ubuntu Server 24.04 Windows Server 2022 Active Directory UFW logrotate

Objectif du projet

Mise en place d'une infrastructure complète de centralisation et d'analyse des journaux système (logs) pour un parc Linux et Windows intégré à un domaine Active Directory. L'objectif est de collecter, structurer en JSON, indexer dans Elasticsearch et visualiser dans Kibana les événements de toutes les machines, avec un système d'alertes automatiques pour la détection d'incidents de sécurité en temps réel.

"Infrastructure de centralisation des logs avec alertes temps réel : rsyslog collecte, Elasticsearch indexe, Kibana supervise."

Architecture de l'infrastructure

Machine IP Rôle
ubulog 192.168.10.1 Serveur rsyslog + ELK Stack (Elasticsearch, Filebeat, Kibana)
clsyslog 192.168.10.x Client Linux – envoi des logs vers ubulog
SRV-RSYSLOG 192.168.10.10 Windows Server 2022 – AD/DNS + NXLog (agent logs Windows)

Flux des données

Clients Linux/Windows → rsyslog (port 514/TCP) → Fichiers JSON
↓
Filebeat → Elasticsearch 8.x → Kibana (dashboards + alertes)

Travaux réalisés

1. Configuration rsyslog – Collecte et structuration JSON
  • Activation réception TCP port 514 (modules imtcp/imudp)
  • Template JSON custom pour chaque log (timestamp, hostname, programme, sévérité, message)
  • Règles de tri par programme : sshd, sudo, systemd, kernel
  • Arborescence : /var/log/central/[hostname]/[categorie]/
2. Déploiement ELK Stack
  • Elasticsearch 8.x : stockage et indexation (index rsyslog-logs)
  • Filebeat : transfert des fichiers JSON vers Elasticsearch
  • Kibana : interface de visualisation (http://192.168.10.1:5601)
  • NXLog sur Windows Server 2022 : transmission des Event Logs Windows
3. Dashboards Kibana
  • Tableau des machines actives (logs par hostname)
  • Camembert de répartition par programme (sshd, sudo, kernel…)
  • Bar chart temporel : évolution des logs dans le temps
  • Dashboard SSH dédié : connexions réussies vs échecs
4. Sécurité et maintenance
  • Pare-feu UFW : SSH:22, rsyslog:514, Kibana:5601 (réseau interne uniquement)
  • Logrotate : rotation quotidienne, 6 mois de rétention, compression .gz
  • Snapshots Elasticsearch automatisés quotidiennement (cron)

Incident simulé – Détection brute force SSH

🔔 Alerte Kibana : Brute Force SSH
  • Simulation : 20 tentatives de connexion SSH échouées générées via commande logger
  • Condition d'alerte : plus de 5 échecs SSH en 1 minute
  • Résultat : alerte déclenchée en temps réel dans Kibana (statut Active)
  • Vérification : dashboard SSH affiche le pic de tentatives avec hostname et timestamps
# Commande de simulation utilisée :
for i in {1..20}; do
  logger -p auth.warning -t sshd "Failed password for hacker from 10.0.0.1 port 22 ssh2"
done

Incidents rencontrés et résolus

① omelasticsearch incompatible avec Elasticsearch 8.x

Le module rsyslog omelasticsearch ne supportait pas HTTPS avec ES 8.x — aucun log envoyé, aucune erreur visible.

✅ Solution : remplacement par Filebeat, outil officiel Elastic pour ES 8.x.
② Guillemets typographiques corrompant les configs rsyslog

Copier-coller depuis un éditeur riche introduisait des guillemets typographiques non parsables par rsyslog.

✅ Solution : réécriture des fichiers avec la commande tee (caractères ASCII purs).
③ JSON mal formé – plusieurs objets sur une même ligne

Filebeat ne pouvait pas lire les logs JSON car plusieurs objets étaient collés sur la même ligne.

✅ Solution : ajout de \n à la fin du template JSON rsyslog (un objet JSON par ligne).
④ Kibana sans permissions sur le certificat SSL Elasticsearch

Après réinstallation d'Elasticsearch, Kibana crashait (EACCES sur /etc/elasticsearch/certs/http_ca.crt).

✅ Solution : chmod sur les certificats + ajout de kibana au groupe elasticsearch.
⑤ Cluster Elasticsearch en état RED après test de restauration

Un index de test resté dégradé (unassigned_shards) bloquait le cluster entier.

✅ Solution : suppression du data stream de test via l'API DELETE _data_stream.
⑥ Alertes Kibana – clé de chiffrement manquante

Impossible de créer des règles d'alerte : "You must configure an encryption key to use Alerting".

✅ Solution : ajout des 3 clés xpack dans kibana.yml + redémarrage du service.

Résultats obtenus

  • Stack ELK opérationnelle : logs Linux et Windows centralisés, indexés et visualisables
  • Dashboards Kibana fonctionnels avec supervision en temps réel
  • Système d'alertes brute force SSH actif (détection sous 1 minute)
  • Archivage automatique 6 mois + snapshots Elasticsearch quotidiens
  • 6 incidents techniques rencontrés, diagnostiqués et résolus
